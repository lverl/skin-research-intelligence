# Skin Research Intelligence

Сервис исследовательских ответов и ежедневного дайджеста об уходе за кожей для владелицы и её подруг. Рабочий интерфейс — Telegram; исходный проект адаптирован под проверяемые источники.

- При старте читать [README.md](README.md), затем последнюю запись [progress.md](progress.md); перед продуктовой работой — PRD и kanban по навигации README.
- Отвечать по-русски. Инвентарь, команды и воспроизведение принадлежат README; текущий этап и причины решений — progress.
- Для новых функций и изменений поведения обязателен SDD: PRD → функция → интерактивный опрос → spec → явное одобрение пользователя → plan → tasks → код.
- До spec уточнить назначение, пользователей, сценарии, KPI, границы, данные, стоимость, ошибки и приёмку; не переспрашивать уже решённое.
- До одобрения spec не писать план реализации, задачи и код. Молчание не является одобрением; не приписывать одобрение задним числом.
- Каждая новая spec: `docs/specs/NNN-short-name/spec.md`; после одобрения — соседние plan.md и tasks.md. Существенная смена границ требует повторного одобрения.
- В spec фиксировать дату, статус, основание одобрения, требования, исключения и проверяемые KPI; в plan — подход, зависимости, риски и проверки; в tasks — ID, критерии, исполнителей и состояния.
- Канбан — единственный бэклог; связывать карточки со spec/plan/tasks и синхронизировать ID и стадии. Идея в бэклоге не разрешает реализацию.
- Три разные роли: A пишет код, B пишет тесты по одобренной spec, C запускает тесты и фиксирует результаты/пропуски; назначать их в tasks до реализации.
- После исправлений C повторяет затронутые проверки. Без независимых проверок не отмечать Done; историческим тестам независимость не приписывать. Для документации достаточно независимой сверки.
- Архитектуру и расписание не менять молча. Правила исследования и терминов читать в [METHODOLOGY.md](METHODOLOGY.md), требования продукта — в PRD.
- Не ослаблять проверку оснований ради прохождения очереди; массовые платные повторы требуют согласованного объёма.
- Секреты и пользовательские скриншоты не публиковать. Python-пакеты — только в `.venv`; команды запуска и проверок — README.
- Временное и завершённые этапы переносить в `_temp/`; ничего не удалять без перечня и явного подтверждения пользователя.
- Исторические заметки сохранять; исправления оформлять новой вехой. Различать локальную проверку, деплой и подтверждение пользователя.
- После значимой работы дописывать веху в progress; последняя запись должна давать точку входа следующей сессии. Внешняя память ссылается на проектные документы.
